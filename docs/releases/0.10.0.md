# LCU 0.10.0

**LCU no longer needs Python.** Install, setup, launch, the Chrome relay and `lcu update` now run on the Node that ships inside the ChatGPT app (`cua_node`) on Linux and macOS. Users need nothing installed beyond the official app and their harness. Computer use itself is unchanged: LCU still hands over to the app's original runtime with the same files, arguments and environment. The port also fixes how setup, `lcu status` and `lcu update` pick the home for non-root runs, and makes the Claude Code relay exit within seconds when its host goes away. Windows remains deferred: the Windows installer was ported too, but it has no live Windows run. The brief is [docs/REMOVE-PYTHON.md](https://github.com/amontlabs/lcu/blob/v0.10.0/docs/REMOVE-PYTHON.md); the change is [#31](https://github.com/amontlabs/lcu/pull/31).

## Changes

- **Python is not required** ([#31](https://github.com/amontlabs/lcu/pull/31)). Python 3.12+ is no longer a prerequisite on any platform. The Linux installer no longer installs `libxres1` or `python3`: the Linux input guard speaks the X11 protocol (X-Resource, XTEST) directly from Node. The Claude Code plugin hook no longer looks for Python before installing LCU. The build tooling and test drivers stay Python and are not shipped.
- **Each release records its Node.** The installer writes `<release>/node-path`, the absolute path of the app's Node (on macOS, `/Applications/ChatGPT.app/Contents/Resources/cua_node/bin/node`). The `bin/lcu*` launchers are `/bin/sh` scripts that run it. If the app is moved or removed, `lcu` says so and asks you to repair the app or reinstall LCU; `lcu --help` still works.
- **The Chrome relay was renamed.** The private native-host copy under `~/.local/share/lcu/browser/<id>/` now holds `lcu-native-host.mjs` instead of `lcu-native-host.py`. The `lcu-native-host` launcher the browser manifest points at keeps its name; it is a short `sh` script that runs the Node recorded for the release. `lcu update` and `lcu browser install` replace the old relay.
- **Install and update downloads.** `lcu update` extracts the release with the system `tar`, after checking the listing as 0.9.7 did and checking the extracted tree again. Downloads are written to a file and hashed there; with a configured HTTPS proxy, or after a failed request, they go through `curl`. `install.sh` refuses group- or world-writable entries and entries owned by another account, and explains why it refuses another account's app for a root install. `install.sh --help` works without the app.
- **Setup, `lcu status` and `lcu update` follow `$HOME` for non-root runs** (`5507f1f`). Setup took the account's home from the user database while the default prefix, `lcu status`, `lcu update` and the agents followed `HOME`, so `env HOME=<other> lcu setup` wrote into the real home. Without `--user`, setup, the installer's setup step, `lcu status` and `lcu update` (including its refresh of the Claude Code mod) now use `$HOME` when it is an absolute, existing directory owned by the caller with no symbolic link on its path, and the user database home otherwise. Root and `--user` are unchanged (root must still pass `--user`). The installer forwards `--user` only when it was given; before, it always forwarded the caller's name. A failed setup's retry command names `--user` only when the caller did.
- **macOS warning for a home that is not the account home** (`0e47a2e`). The original Computer Use client finds the ChatGPT helper's socket and its approved-app list under `HOME`, so agents configured in another home fail with `native pipe startup failed` unless `SKY_CUA_SERVICE_NATIVE_PIPE_PATH` names the helper's socket. Setup on macOS now says so when the home it configured is not the account's home folder.
- **Claude Code relay exits within seconds when its host dies** (`a5bc374`). With a `js` call in flight, killing Claude Code (SIGINT, SIGTERM or SIGKILL) left the relay and the original runtime running until that call ended (60 s in the macOS check, 22 s in an earlier one), after which the relay crashed with `EPIPE`. 0.9.7 behaves the same. The relay now closes its server first, which cancels in-flight calls upstream and starts their Interrupt cleanup, gives that drain at most 2 s, then closes the original server. On macOS every process the client started was gone 5–7.4 s after the signal; the remaining time is the original runtime's own exit. The Codex relay is unchanged.
- **Host stderr kept off Pi, OMP and Hermes terminals** ([#30](https://github.com/amontlabs/lcu/issues/30), `f230511`). These harnesses run the shared client in-process, so the original MCP process's stderr (turn-ended timing, cleanup failures, stale-service recovery) was drawn into their input area. That stderr is now drained and recorded as a classified diagnostic event (never its text), Hermes logs it through Python logging, and the in-process host guard no longer prints its refusal (the approval log records it). The Claude Code and Codex relays still inherit stderr.
- **Error and help wording may differ.** Messages are still `LCU: <message>` with exit status 1. A usage error is one line naming the command, such as `lcu browser: Unknown action 'frob'; use install or status.`, with a pointer to its `--help`, and exit status 2. Help texts start with `Usage:`. Commands, flags and exit codes are unchanged, but the text is Node's, not Python's (no argparse-style usage blocks, no `[Errno N]`).
- **Exit status after a signal.** Where `lcu` waits for the original server (macOS, Windows), a server ended by signal N now gives exit status 128 + N, the shell convention. 0.9.7 gave 256 − N.
- **Lock waits.** Locks stay kernel flocks on the same files 0.9.7 locks (`setup.lock`, the browser host lock, `.lcu-origins.lock` and the install marker), so the two releases exclude each other and a crashed holder releases by exiting. A wait longer than a second now prints `LCU: waiting for another LCU process to release …`.
- **Faster startup on Linux; about the same on macOS.** On Linux x64 (end-to-end check, medians), `lcu --version` takes 64 ms against 114 ms for 0.9.7, and `lcu-session --help` and `lcu-codex-sandbox --help` 32 ms against 64 ms. On macOS the gain is small, because both releases spend most of their startup in the app's signature checks: medians of 670 ms against 686 ms for `lcu --version`, 708 against 741 ms for `lcu status`, 768 against 789 ms for `lcu doctor`, and about 0.90 s against 0.95 s from starting a registered MCP command to a completed `tools/list`.
- **Windows (deferred).** `scripts\install.ps1` is the only Windows entry point; it checks the registered Store app and runs that app's own `node.exe` on the Node installer. Windows registrations name the account-local `<prefix>\lcu.cmd`, npm `.cmd` shims run through `cmd.exe`, and batch-file arguments are escaped instead of refused. None of this has run on a live Windows desktop, and no Windows archive is published.

The original runtime, tool schemas and instructions are unchanged. No new tested app pairs are claimed: ChatGPT 26.930.61225 with CUA 0.0.27/20260927214556-b77d38801cca, used for the macOS checks below, is not in `tested-versions.json` (a warning only).

### Upgrading from 0.9.7

`lcu update` from 0.9.7 installs 0.10.0 in place: 0.9.7 runs the new archive's `scripts/install.py` (`install_macos.py` on macOS) with its own Python, and that file is now a stub without logic that hands over to `install.sh` with the same arguments. Agent registrations, saved choices and the release layout carry over, and reinstalling 0.9.7 rolls back. On macOS, 0.9.7's own `lcu setup` and `lcu update` to 0.10.0, then a rollback by reinstalling 0.9.7, were run against the real home with both registrations working at each step. The setup lock was checked against a running 0.9.7 `lcu setup` in both directions: each release waited for the other, and `kill -9` of the holder released it within about 1.2 s. On Linux the upgrade and rollback are covered by the end-to-end check and the lock interop by a unit test against `fcntl.flock`.

On macOS it is 32 out and 36 in: `lcu/macos_host.py` becomes `lcu/macos_host.mjs`, and `scripts/install.py` is dropped because 0.9.7 runs `scripts/install_macos.py` there, which stays as the stub. The `bin/` launchers keep their names and are now `/bin/sh` scripts; `node-path` is written by the installer and is not in the archives. Nothing else in the member lists changed. Archives contain no OpenAI application binaries or copied original instructions. The macOS archive was built from `/Applications/ChatGPT.app` (26.930.61225). Archives are not byte-reproducible across builds; the Linux archives above are the ones that each gate run built and tested.

## Not verified

- **Any live Windows run**: `install.ps1` with the Store app, a computer-use action, the upgrade from 0.9.7, and the lock files against a running 0.9.7 host. Windows coverage is CI and structural checks only.
- **The task-owned macOS verification guest.** Every macOS check above ran on the maintainer's Mac.
- **The Chrome browser relay on macOS**, including the renamed `lcu-native-host.mjs`. It was not part of either macOS run.
- **Closing stdin of a real client mid-call.** Claude Code finishes its turn before exiting and `codex exec` reads its prompt to EOF, so the relay's stdin case was covered by a minimal MCP client only.

Known issue, not a change: `typeText` under the French AZERTY layout loses characters in the original runtime (the test string came out as, for example, `Héllo wrld —   Ω`). 0.9.7 gives the same results, and LCU does not touch text input on macOS; the exact bytes above came from `setValue` or `paste`. Everything listed under "Not verified" in [0.9.7](https://github.com/amontlabs/lcu/blob/v0.10.0/docs/releases/0.9.7.md) still applies.
